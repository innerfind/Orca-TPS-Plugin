# 每日 Token 天梯榜设计

## 榜单规则

| 项目 | 规则 |
| --- | --- |
| 参与 | 所有 Orca 插件用户都可以用 GitHub 登录。登录后可以看榜和提交。 |
| 日期 | 服务端按北京时间划分榜单日，零点开启新榜。插件和网页按访问者的本地时区显示提交时间，榜单日期仍使用北京时间。 |
| 分数 | 使用插件在提交时已采集的当日 Token 总量。新输入、输出、缓存写入和缓存读取都计入，本机和远程用量沿用现有数据来源及去重规则。 |
| 排名 | 提交成功后立刻上榜。按 Token 总量从高到低排，同分时先提交者在前。榜单显示名次、GitHub 用户名、Token 总量和提交时间。 |
| 提交次数 | 同一个 GitHub 账号每个榜单日只能成功提交一次。重复提交直接拒绝，用户不能修改或撤回。 |
| 定时提交 | 默认关闭。用户可以在插件里设定本地时间，Orca 正在运行时按设定提交。当天错过定时点可以手动提交。 |

## 组件与数据流

| 组件 | 职责 |
| --- | --- |
| Orca 插件 | 在「对话 TPS」提供天梯榜入口、GitHub 登录、当日用量预览、手动提交和定时设置。插件负责统计，提交只发送榜单日期和 Token 总量。 |
| 榜单服务 | `server/` 下维护独立的 Node.js 服务。提供登录、当日榜、提交状态、提交及网页管理后台。所有榜单接口都检查登录和封禁状态。 |
| SQLite | 保存 GitHub 账号 ID 和用户名、每日提交标记及成绩、提交错误和当天锁定记录、必要的会话及管理员操作记录。 |
| HTTPS 入口 | Caddy 接收公网请求并转发给只监听本机的榜单服务。插件使用发布配置中的固定 HTTPS 地址。 |

### 当日用量和提交

现有用量索引按设备的本地时区归日。榜单汇总从每条请求的完成时间按 `Asia/Shanghai` 另存每日总量，本机和远端都使用同一口径。已有索引升级时按原有增量刷新机制补齐榜单用量，已经存下的本地日汇总无法直接换算为北京时间用量。提交前读取最新可用快照，当日用量尚未就绪时提示用户。当日已汇总的远程用量可以继续使用上次成功读取的数值。

手动提交前显示榜单日、Token 总量和提交后不能撤回的提示。定时提交使用相同的统计和服务端规则，账号未登录、当日用量尚未就绪或当天已经提交时显示对应状态。服务端以收到请求时的北京时间为准。账号身份从会话中取得，提交时间由服务端记录。

每个提交动作在 HTTP 请求头中带一个请求标识。响应丢失时，插件先查询提交状态。相同账号当天再次提交会被明确拒绝。原样重试同一请求不会增加错误次数。复用请求标识发送不同内容视为新的错误。数据库通过账号与日期的唯一约束和事务保证两台设备同时提交时只接受一条。

### 登录与管理员

插件使用 GitHub 设备授权，管理网页使用 GitHub 网页授权。两种入口共用榜单服务的账号。服务端从 GitHub 取得不可变的账号 ID 和用户名，再发放榜单自己的登录凭据。插件通过 Orca 的加密密钥存储保存凭据。系统密钥存储不可用时仅在本次运行中使用凭据，重启后需重新登录。

部署时在服务端设置管理员的 GitHub 已验证邮箱。管理员首次绑定通过一次 GitHub 邮箱授权确认归属，成功后按 GitHub 账号 ID 判断管理权限。普通用户登录只需基本身份数据。GitHub 应用密钥和管理员邮箱通过服务器配置提供。榜单用 GitHub 用户名展示用户身份。服务器收集的用量数据限于榜单日期和 Token 总量。

### 自动限交与管理

| 情况 | 处理 |
| --- | --- |
| 提交通过 | 账号有效、当天未锁定也未提交、日期是当前榜单日，Token 总量为大于零的安全整数并在服务端配置的范围内。检查通过后立刻入榜。 |
| 提交错误 | 已登录账号提交重复成绩、不合规的日期或数值、非法请求格式时，计一次错误。登录过期、网络或服务器故障、同一次请求的原样重试不计。 |
| 当天锁定 | 同一账号在当前榜单日内，最近 10 分钟累计到第 5 次错误时立即锁定提交，直到北京时间次日零点。锁定记录保存到 SQLite，账号仍可看榜。 |
| 封禁 | 管理员按 GitHub 账号封禁和解封。封禁期间榜单和提交接口都拒绝该账号，包括已经建立的会话。成绩可由管理员另行删除。 |
| 删除与清空 | 管理员能删除单条成绩、清空指定日期或全部榜单。清空需要二次确认。当天已经成功提交的标记保留至该榜单日结束。后台记录操作者、时间和操作范围。 |

提交规则由服务端自动执行。校验能拦截重复请求和不合规数值，本地日志的真实性仍取决于数据来源。登录、提交和查榜接口各自设定请求大小与频率上限，后台变更操作检查管理员身份及网页请求来源。

## 部署和验收

使用已准备的 Ubuntu 24.04 LTS 专用服务器。Node.js 24 LTS 以独立系统账号运行，`systemd` 负责开机启动和故障重启，数据库存于持久磁盘。使用公网 IP 作为正式入口。配置 GitHub 网页登录的 HTTPS 回调并启用设备授权。公网 80 和 443 端口可达后，用 Certbot 申请受信任的 IP 证书，自动续期后让 Caddy 重新加载证书。每天在线备份 SQLite，并验证备份可以恢复。[GitHub 授权流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) · [IP 证书部署](https://letsencrypt.org/2026/03/11/shorter-certs-certbot) · [SQLite 在线备份](https://sqlite.org/backup.html)

| 范围 | 通过标准 |
| --- | --- |
| 服务端和数据库 | 两个账号能正常上榜。同账号并发提交只写一条。重复提交直接拒绝，删成绩后同日仍不能再交。 |
| 防刷和日期 | 第 5 次错误触发当日锁定，窗口外的错误和上一个榜单日的错误不累加。重启后锁定仍有效，零点恢复提交。锁定账号能看榜，封禁账号无法看榜或提交。 |
| 插件和现有统计 | 本机与远程在跨北京时间零点时正确归日，图表仍使用各自的本地日历。手动和定时提交共用规则，断线后可查提交结果。现有统计测试通过。 |
| 管理与上线 | 普通账号无法操作管理后台，已验证的管理员能完成封禁、解封、删除和清空。真实 GitHub 登录、IP 的 HTTPS 信任与续期、集中提交和数据库恢复均通过联调。 |
